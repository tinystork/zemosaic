## 2. Le défaut structurel mis en évidence

RUN ». C'est exactement ce que P1 doit corriger, sans toucher aux marges.

## 4. Contrats figés, tâches obsolètes, propagation

* **Figés et jamais modifiés** : backend CPU, classe `external_spool`, tuile
  spool 128, halo 16, membreships/layout/frame ids, science (normalisation,
  pondération, rejet, combine), N par cellule, **marges** (15 %) et facteur
  90 %.
* **Seul paramètre mobile** : `column_batch` (staging). Le produit documente
  déjà que les charges utiles sont identiques bit à bit entre tailles de lot
  (preuve réelle M106) ; le lot n'est pas dans l'identité scientifique.
* **Le contrat est lu DANS le bundle, pas passé en argument (F1)** :
  `_r55_active_apply` fait `external_contract = _r55_external_contract(bundle)`
  (`mode.py:14371`) et construit la tâche externe avec **ce** contrat
  (`mode.py:14434-14436`) ; l'exécuteur lit `tile_size`/`column_batch` dans le
  **slot 7 de la tâche** (`_prepare_stack_cell`, `mode.py:6643-6650`), jamais
  dans le planner. Appliquer l'applicateur au **bundle initial inchangé**
  régénère donc des tâches à `column_batch = 7296` alors que le record
  durable et le gate de propagation affirment `6912` : le shrink serait admis
  sur le papier et **non exécuté**. Le contrat successeur doit être attaché à
  un **NOUVEAU bundle** (ou passé explicitement à l'applicateur) *avant*
  `_r55_active_apply`. Le précédent correct est le sélecteur lui-même
  (`mode.py:8493-8530` : `shrink_frozen_column_batch` puis re-pricing
  `estimate_external_working_set(..., to_batch ...)`).
* **Tâches obsolètes après TOUT remplacement de bundle (F2)** : `pending_tasks`
  est construit **une seule fois** depuis `start_bundle.cell_tasks`
  (`mode.py:21627-21634`) ; après `_r55_run_checkpoint` le caller ne réassigne
  que `bundle`/`candidate`/`mapping` (`mode.py:22331-22333`) et la vague prend
  `wave_tasks = pending_tasks[start:end]` (`mode.py:22356-22358`). La recovery
  bounded existante réassigne `all_tasks = _recovery["tasks"]`
  (`mode.py:22137-22139`) **mais pas** `pending_tasks`, alors que
  `_bounded_run_recovery` renvoie bien `_new_tasks = list(_bnd.cell_tasks)`
  (`mode.py:21911`) : ce chemin est donc aujourd'hui un **no-op trompeur**
  (tâches denses ré-exécutées sous un bundle borné). **Ce précédent ne doit
  pas être copié** ; il doit être corrigé par P1.
* **Algorithme de remap sûr (obligatoire, P1)** — applicable au shrink de lot
  **et** au fallback dense→bounded existant :
  1. identité = `cell_id` : construire `new_by_id = {str(t[0].cell_id): t for t
     in new_bundle.cell_tasks}` ; exiger `len(new_by_id) ==
     len(new_bundle.cell_tasks)` (aucun doublon) et `set(new_by_id) ==
     set(old_by_id)` (même ensemble de cellules, ni perte ni ajout) ;
  2. `pending_ids` = suite ordonnée des `cell_id` de `pending_tasks` (l'ordre
     canonique du plan, pas l'ordre d'achèvement) ; vérifier que chaque id
     existe dans `new_by_id` ;
  3. `pending_tasks = [new_by_id[cid] for cid in pending_ids]` — **les tâches
     déjà exécutées ne sont pas remplacées** (résultats acceptés conservés) et
     aucune tâche ne peut être dispatchée deux fois (le compteur
     `_cpu_cell_progress_state` reste indexé par `cell_id`) ;
  4. `total_tasks = len(pending_tasks)` ; `offset` et la progression déjà
     commitée sont **préservés** (aucun recalcul depuis zéro) ;
  5. `all_tasks` est reconstruit de la même façon depuis `new_bundle` pour
     l'assemblage/les compteurs, en conservant l'ensemble complet des cellules
     attendues ;
  6. génération/fence avancée **avant** la vague suivante, puis reprise
     normale ; l'ordre canonique et les ids restent la seule clé.
* **Sites de copies du contrat** : `working_set_block` (manifeste),
  `external_contract` (bundle), `cell_specs`/`cell_tasks` (exécution),
  `state.admission.working_set.column_batch` (durable). Les quatre doivent
  être mis à jour depuis **une seule** valeur (le record durable), jamais
  re-dérivés indépendamment.
* **Hash de plan** : `active_final_plan_hash` couvre candidat + mapping +
  identité + enveloppe ; un changement de lot modifie l'enveloppe (host_peak)
  et doit donc produire un nouveau hash publié, sans toucher l'identité.
